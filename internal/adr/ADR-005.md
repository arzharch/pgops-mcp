# ADR-001: Deny-by-default SQL classifier

**Status:** Accepted · **Date:** 2026-08-24

## Context
Agents will send arbitrary SQL. We must decide read vs write vs destructive before
execution. Any misclassification of a dangerous statement as safe is catastrophic;
over-classification is merely annoying.

## Decision
The classifier is deny-by-default: any statement it cannot confidently recognize as a
pure read (SELECT/WITH/EXPLAIN with no data-modifying CTEs, no function calls known to
write) is treated as the most-dangerous applicable class. Unknown → destructive path.

## Consequences
- False positives (safe statements requiring confirmation) are acceptable and tunable.
- Requires careful handling of CTEs with INSERT/UPDATE/DELETE inside, and volatile
  functions; both handled in Phase 2 with table-driven tests.
- Security reviewers can audit one small module instead of the whole server.

# ADR-002: stdio transport first, HTTP later

**Status:** Accepted · **Date:** 2026-08-24

## Context
MCP servers can expose stdio or Streamable HTTP. Target users run Claude Desktop,
Cursor, VS Code locally against a local Postgres.

## Decision
Ship stdio-only for v0.1. Design tool layer transport-agnostic so Streamable HTTP can be
added behind a flag post-v1 without touching tools.

## Consequences
- Zero network attack surface at launch; auth problem deferred rather than solved badly.
- Remote/team use cases explicitly out of scope until HTTP lands.

# ADR-003: Own migration ledger over external tools

**Status:** Accepted · **Date:** 2026-08-24

## Context
Migration apply/rollback needs version tracking. Options: integrate sqitch/flyway/alembic,
or maintain our own ledger table.

## Decision
Own ledger (`pgops_migrations`): id, name, checksum, applied_at, duration, status.
Checksums detect drift; statuses support crash recovery (in_flight → applied | failed).

## Consequences
- No external dependency; agent-native UX; full control of semantics.
- Interop with existing migration tools is a possible later adapter, not a v1 goal.

# ADR-004: Lock-impact analysis via heuristics + known-safe patterns

**Status:** Accepted · **Date:** 2026-08-24

## Context
Exact lock-duration simulation on Postgres is not feasible externally. But operation
classes have well-known behavior (e.g., ADD COLUMN nullable = metadata-only;
ALTER COLUMN TYPE = rewrite; CREATE INDEX = lock vs CONCURRENTLY).

## Decision
Classify each DDL step into an operation class, combine with live table size to produce
an estimate + confidence + plain-language reasoning. Where a risky step has a known safe
multi-step equivalent (NOT VALID + VALIDATE, CONCURRENTLY), propose the rewrite.

## Consequences
- Estimates are honest heuristics, never presented as guarantees.
- The pattern library grows with experience and becomes a differentiator itself.

# ADR-005: testcontainers-based integration tests, no guardrail mocks

**Status:** Accepted · **Date:** 2026-08-24

## Context
Guardrails that pass against mocked SQL execution prove nothing — Postgres semantics are
the adversary.

## Decision
All guardrail/migration/explain tests run against real Postgres spun up by testcontainers
(per-session container, per-test schemas). CI runs Linux containers; local dev uses Docker
Desktop.

## Consequences
- Slower suite (~minutes), fully accepted. Correctness > speed here.
- Seeded scenario fixtures (slow queries, big tables) live in `tests/fixtures/sql/`.
