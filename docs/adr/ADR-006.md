# ADR-006: Scaling path — local-first core, shared-service tier as a deliberate evolution

**Status:** Accepted · **Date:** 2026-08-25

## Context

pgops-mcp v0.1 is a single-node, local-first tool: one process per user, stdio to the
client, pointed at a DSN. That is correct for its primary audience (a developer running
AI agents against their own database) and it is *not* an accident — the PRD's non-goals
explicitly exclude hosted service and multi-database fleet management.

But "local-only" invites two wrong conclusions:

1. That the architecture *can't* scale — it can, and parts of it already did (HTTP
   transport, JWT auth, scoped tokens shipped in Phase 6b).
2. That scaling is just "run more copies" — it isn't. Two real blockers exist:
   in-memory state (plan cache, confirmation tokens) and per-process audit logs.

This ADR records what changes at each scale tier, what stays safe, and where the honest
limits are.

## Decision

Scaling proceeds in three tiers. Each tier reuses the same safety core unchanged; only
the edges (state, transport topology, deployment) change.

### Tier 1 — Local (shipped)

One process per user, spawned by their MCP client over stdio.

```
Claude Desktop ──stdio──> pgops-mcp ──> user's Postgres
                              └──> ~/.pgops/audit.jsonl
```

- In-memory plan/token state is fine: one process, one user.
- Local audit file is fine: one writer, incident review reads it directly.
- No network surface: nothing to harden beyond what exists.

### Tier 2 — Shared team server (designed for; mostly built)

One pgops-mcp instance per team, reached over HTTP+JWT, pointing at a shared dev/staging
database. Multiple agents from multiple engineers authenticate with scoped tokens.

```
N agents ──HTTP+JWT──> 1 pgops-mcp ──> shared Postgres
                           └──> centralized audit sink
```

What already works:
- Auth: RS256 public-key verification is stateless — any instance verifies tokens with
  no shared secret. Scopes (`pgops:read/write/admin`) limit *what* each agent can do.
- Concurrency: async pools handle concurrent readers; writes serialize through the small
  readwrite pool, which for a team DB is arguably a feature (one write queue = fewer
  surprises).

What must be added (the actual work):
1. **Per-session DSN isolation.** Today every authenticated caller shares one
   `ConnectionManager`. Tokens must carry (or map to) a target database, so agent A on
   project X cannot reach project Y's schema even with `pgops:write`.
2. **Centralized audit sink.** The JSONL file becomes a structured log stream (OTel or
   syslog or a write-ahead append API). The *format* already carries everything needed
   (actor, verdict, sql hash); only the sink changes.
3. **Externalized ephemeral state.** Plan cache and confirmation tokens move from
   in-memory dicts to Redis (or Postgres itself). Both are already TTL-scoped and
   content-addressed (tokens bound to sha256(sql), plans bound to checksums), so this is
   mechanical, not a redesign.
4. **Rate limiting / quota per token subject.** One misbehaving agent shouldn't starve
   the pool for everyone. The acquire-timeout → `POOL_EXHAUSTED` machinery gives the
   error signal; enforcement per-subject is new.

Safety posture: unchanged. Classifier, guardrails, elicitation, ledger, rollback — all
operate per-request and don't care how many peers the server has.

### Tier 3 — Hosted multi-tenant (possible; explicitly not v1)

Many customers, many databases, pgops as a control plane. This is where it stops being
"the same thing with more instances" and starts being a different product:

- Network-level isolation per tenant (the Docker socket story especially — Tier 3 means
  container tools need per-tenant daemon boundaries or removal).
- Compliance surface: audit retention, tenant data segregation, SOC-2-style controls.
- Per-tenant key management for the RS256 model (or migration to OIDC federation).

The PRD non-goal ("not a hosted/cloud service") stands until someone decides otherwise;
Tier 3 is recorded here so the boundary is explicit rather than discovered by accident.

## Consequences

- The claim "local-only" is retired in favor of "local-first, three documented tiers."
- Tier 2 work items (DSN isolation, audit sink, externalized state, rate limits) are now
  named deliverables rather than vague "scaling concerns."
- Nothing in Tier 1 needs to change. The tiers are additive.
- The strongest argument *for* keeping Tier 1 as the default remains true: when the
  database is local, the safest place for the operator credential is the user's own
  machine, under their own account, with no network listener at all. Moving to Tier 2
  buys team collaboration at the price of a network attack surface that must then be
  defended forever. That trade should be made deliberately, per deployment — which is
  exactly what the transport-bound auth design enables.
